## 1. 现状识别系统架构（实测代码，非文档）

来源：`app/src/main/java/com/zfdang/chess/recognition/OnnxBoardRecognizer.kt`
（移植自 Shirakawa-Kotone/chinese-chess-helper，模型来自 TheOne1006/chinese-chess-recognition / HF yolo12138）。

```
原图 (EXIF 矫正, ImageLoader)
 → RTMPose 4 角点模型 4_v6-0301.onnx  (256×256 仿射, SimCC /512 argmax)
   两种缩放假设(按宽/按长边) × {原图, 旋转180°} = 4 候选
 → 透视矫正 450×500 (边距50) → 中心裁 400×450 → 缩放 280×315
 → ImageNet 归一化 (RGB, mean/std 与训练侧一致)
 → SwinV2-nano 分类器 nano_v3-0319.onnx  → [1,90,16] logits（一次前向出全部90格）
 → argmax = 类别; 置信度 = top1-top2 logit margin（未 softmax）
 → 后处理: 仕/相(a/b) 侧别按行范围强制修正 (r>=5→红, 否则→黑)
 → 4 候选按 90 格平均 margin 择优; avg<0.6 时底边角点 dy 扫描精修
```

**模型真实类别表（16 类，与训练配置 `dict_cate_names` 逐字核对）**：

| 索引 | 0 | 1 | 2-8 | 9-15 |
|---|---|---|---|---|
| 符号 | `.` | `x` | `K A B N R C P` | `k a b n r c p` |
| 含义 | 空位 | **"其他"（other）** | 红：帅仕相马车炮兵 | 黑：将士象马车炮卒 |

上游 README 原文：*"黑子…对应简写`kabnrcp`、红子…对应简写`KABNRCP` + 其他 简写`x` + 空位 简写`.`"*。

**结论 1：现有模型的 `x` 是杂项类（训练中主要承载非交叉点物体/不明物体），不是揭棋暗子类别。**
模型从未被教过"暗子"这个概念。Android 端更是把 `x` 与 `.` 一样丢弃（`if (ch == '.' || ch == 'x') continue`），即模型即使输出了 x 也会被当成空位。

**结论 2：模型架构确认**。分类器 = SwinV2-nano（embed_dims=72, depths=[2,2,6]）+ 10×9×16 线性颈，单头 16 类联合输出（颜色+身份联合类别，无独立颜色头）。训练输入 280×315（`Resize scale=(280,315)`，与 Android 推理一致）；ONNX 为动态 batch/H/W，opset 11。

## 2. 真实揭棋素材逐格诊断（12 张截图 × 90 格全量比对）

方法：PC 端 1:1 复刻 Android 管线（`xiangqi-vision/scripts/pc_recognizer.py`，onnxruntime CPU），逐格输出 top1/top2/margin/完整 logits；以人工真值（格子拼贴图 + 局部放大核验）比对。真值与统计脚本：

- 真值：`xiangqi-vision/data/truth_jieqi_shots.json`（167 暗子 / 134 明子 / 779 空位）
- 评估：`xiangqi-vision/scripts/eval_baseline.py`
- 过程产物：`xiangqi-vision/out/`（diag 逐格 JSON、warp 图、格子拼贴图、原图反投影叠加图）

### 2.2 暗子为何被随机猜成明子（根因 RC1）

模型没有暗子类。暗子的外观（木色圆盘+环形刻纹，无文字）落在训练分布之外，模型按"上下文图案匹配"强行归类：

- **开局阵型（第1/2/6张，共 80 个暗子）：0% 输出 x**。整行暗子被识别成标准开局布局——第 1 张黑方底线被识别为 `RNbakabNR`（标准车马炮士象阵！），红方底线 `RNBAKABNR`，兵线全部识别为 `P`（还是红兵）。这是训练数据中"开局满阵"图像的先验记忆。
- **散落暗子（中局，第3/4/5/9张）：部分输出 x**（最好 7/9）。x 类对"无字圆盘"有微弱响应，但极不稳定。
- 另有 13.2% 的暗子直接被判为空位（`d`）。

同一暗子在相邻两帧中可能分别被判为 `x`/`N`/`P`/`.`（第4/5张的 h9 依次为 `.`→`N`），输出毫无一致性，且 margin 与正常明子相当（全图平均 margin 0.71-0.79，与识别正确的图无明显区分）——**仅靠阈值无法挽救，必须重新训练**。

### 2.3 "红黑颜色识别错误"的真相（根因 RC2 + RC1，RC3 次要）

拆开统计后，用户感知到的"明子颜色错误"由三个不同来源构成：

**RC2（占颜色错误的大头，纯后处理 Bug）：仕/相侧别按行范围强制修正。**
`finishRecognition()` 中：
```kotlin
if (lower == 'a' || lower == 'b') {
    side = if (r >= 5) 'R' else 'B'
}
```
普通象棋中仕/相不过河，此修正基本无害（且能掩盖模型对仕/相的颜色误判——这也是它当初被加上的原因）。但揭棋中**明士可出九宫、明象可过河**（已按参考项目实现），于是：

- 黑士走到红方半场（s3/s4/s5 e6）→ 被强制改成红仕 `A`（5 处）
- 黑象走到红方半场（s8/s9 h8/b8）→ 被强制改成红相 `B`（5 处）
- 更糟：即使模型输出正确（`a`/`b`），也会被覆盖成错误颜色 —— 该 hack 在揭棋场景下**主动破坏正确结果**。

**RC1（颜色错误的第二大来源）：暗子被猜成明子时，颜色随之随机错。**
黑方半场的暗子被识别为红车/红马/红兵（如第1张黑方底线 `RN` 为红色大写、兵线 5 个 `P` 全红），用户看到的就是"黑白颠倒"。
（在侧别已知的暗子误判中，24/88 侧别错误；红方半场暗子则大多"碰巧"红方正确——行先验所致。）

**RC3（真实模型颜色/身份错误，占比很小但存在）：**
- `黑士a→黑卒p` ×5（颜色对、身份错：黑士字形被认成黑卒。经放大核验确认 5 处真值均为"士"）
- `黑马n→红马N` ×1（s9 c6，同字形纯颜色错）
- 其余车马炮（同字形颜色区分类）在本组素材中全部正确；兵/卒、仕/士、相/象（异字形对）除上述外均正确。

**结论：明子颜色准确率本身 ≈ 94%（126/134，若剔除 RC2 强改的 8 处则 ≈ 94-100%）。颜色问题的主要修复手段是删除/替换行范围 hack（后处理），而非重训模型；暗子问题才是必须重训的部分。**

### 2.4 空位与置信度

- 空位准确率 97.69%，18 个假阳性中 11 个来自 s11（见 2.5），2 个来自 s10 f0（空格被判 `b`）。
- 置信度=margin 在明子/空位上区分度尚可，但在暗子上**完全失效**（暗子被猜成明子时 margin 同样高达 0.7+）→ 拒识不能只靠 margin，还需类别级校准（暗子类与"无字圆盘"响应）与一致性校验。

### 2.5 角点/透视质量

- 12 张全部成功产出可用 warp；但 s11（17:36:21）出现约半格的网格错位（帅的圆盘横跨 c3/d3 两格），导致 11 个空位假阳性与若干错位判断。s6/s7/s8 有轻度字形压扁（角点略偏）。
- 现有 dy 精修只在 avg<0.6 时触发，s11 avg=0.777 不会触发精修 → 精修触发条件需要加入"结构校验"（如将帅格必占、暗子环检测等）而非仅 margin。

## 4. 修复方案（进入第二/三/四阶段）

1. **新模型（揭棋专用，普通象棋模型保持独立不动）**：同一 SwinV2-nano 骨干 + 单头 **18 类**：`.`(空) / `X`(红暗) / `x`(黑暗) / 红 KABNRCP / 黑 kabnrcp。去掉旧 "其他"类（该类在本场景由拒识机制承担）。选择单头而非多任务头的理由：现有颜色/身份联合类别在实测中颜色准确率已 ≈94%，颜色错误的根因是后处理而非表征不足；单头改动最小、可直接复用预训练骨干权重、Android 后处理完全同构。
2. **删除行范围侧别 hack（仅揭棋模式）**：暗子颜色由模型输出（天天象棋的暗子背面环纹带红/绿侧别信息——已用像素统计验证：红方暗子环带 G-R≈-53、黑方 ≈-44，人脸部分完全一致，可学习）。
3. **拒识机制**：margin 阈值（按类别分组校准：空位/暗子/明子身份/明子颜色）+ 结构一致性校验（将帅各 1、暗子环带响应、行先验仅作提示不强制改写），低置信度格进人工校对。
4. **训练数据**：
   - 真实：12 张截图逐格真值（已有）；
   - 合成：从真实截图抠取棋子 sprite（含两种暗子、全部明子），按揭棋合法摆法随机合成整盘图（海量、带精确标签），随机阴影/亮度/缩放扰动；合成与真实分离标记；
   - 评估：全部 12 张真实截图作为独立测试集（sprite 泄露风格但不泄露位置布局，报告中如实说明）。
5. **Android 集成**：识别器加模式开关（normal 用旧模型旧逻辑，jieqi 用新模型新逻辑），扫描→校对→`JieqiGameState.buildImportFen` 闭环沿用现有实现（已支持 X/x 暗子编辑与池推导）。
